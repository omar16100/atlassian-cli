# Changelog and release notes

shipped in v0.9.2 (PR #140)

## Problem

Issue #138 reported two related gaps.

Releases carried no notes. The last release with any was 0.4.2, in June 2026.
Every release since, 0.4.3 through 0.9.1, has a body containing only cargo-dist's
install instructions and the asset download table. A user deciding whether to
upgrade had nothing to read, and had to diff tags by hand to find out whether a
fix had shipped.

What notes existed before that were inconsistent in kind. 0.1.8 through 0.2.6
carried generated commit lists, from the release-please changelog that was in the
repository at the time and was removed when release-please was dropped in 0.3.3.
0.4.0 through 0.4.2 carried hand-written notes. Everything else carried nothing.
(Verified with `gh release view` across all 41 release entries.)

There was no changelog. The nearest thing was the repository-root `todo.md`, a
running developer log of roughly 3000 lines. It records what was done and why in
detail, which makes it valuable during development and useless as an upgrade
guide: it is not organised by version for the reader, it does not separate
user-visible change from internal churn, and it is not something to point a user
at.

## Design notes

The release pipeline already supported release notes. `.github/workflows/release.yml`
is generated by cargo-dist, and its `host` job creates the release with
`gh release create --notes-file`, where the notes come from cargo-dist's
`announcement_github_body`. cargo-dist builds that value by looking for a
changelog at the workspace root, parsing it, and extracting the section whose
heading matches the version being released.

So the whole of the release-notes half of the issue is delivered by adding a
correctly formatted `CHANGELOG.md`. No workflow was modified.

Decisions taken:

- **Keep a Changelog 1.1.0 format**, as the issue proposed. Headings are
  `## [X.Y.Z] - YYYY-MM-DD`, categories are Added / Changed / Deprecated /
  Removed / Fixed / Security, and compare links sit at the bottom of the file.
  The heading format is what cargo-dist matches on, so it is load-bearing, not
  cosmetic.
- **All 37 tags backfilled**, dated from each tag's creation date. Entries for
  0.5.0 and later are itemised with pull request numbers. Earlier releases are
  summarised, because the early history was rewritten during 0.5.0 and some
  original commits no longer resolve. The file says so, near the top.
- **Only user-observable change is listed.** Formatting commits, lint fixes,
  refactors with no behaviour change, documentation-only work on the separate
  project site, and dependency bumps that closed nothing were left out. A
  dependency bump that closed an advisory is listed under Security with its
  RUSTSEC ID.
- **No `.github/release.yml`.** GitHub's native generated notes are never
  invoked, because cargo-dist always passes `--notes-file`. A category config
  file would be config that never runs.
- **No `cargo-release` `pre-release-replacements`.** The tag is pushed by hand,
  so a hook that only fires under `cargo release --execute` would be equally
  dead. The promotion step is documented instead.

Alongside the changelog, `AGENTS.md` was added at the repository root. It carries
the workspace layout, the checks to run before committing, the documentation
conventions, the rule that every user-facing change updates `[Unreleased]` in the
same pull request, and the release runbook. That runbook previously existed only
as a single log entry in `todo.md` from December 2025. `CONTRIBUTING.md` gained
Changelog and Releasing sections pointing at it, and its reference to a
non-existent `CLAUDE.md` was corrected.

Two stale version pins were fixed in passing: the five internal path
dependencies in `crates/cli/Cargo.toml` were still on `0.9.0` after the 0.9.1
bump. They are semver-compatible with the workspace version, so nothing broke,
but they drift further with each release. The release runbook in `AGENTS.md` now
names them as step 2.

## Limitations

- The bodies of the existing GitHub Releases were not rewritten. The changelog is
  the record for those versions; their release pages are unchanged.
- The release page has leftovers from the release-please era, before the move to
  cargo-dist alone in 0.3.3. `gh release list` shows 41 entries against 37 tags:
  four abandoned drafts (0.1.9, 0.2.4, 0.2.5, 0.2.6), each duplicating a
  published release for the same tag. Cleaning those up is release-page hygiene,
  not part of this change.
- Promoting `[Unreleased]` into a dated section at release time is manual. It is
  step 1 of the runbook.

## Tests

- `dist plan --output-format=json` was run before tagging and
  `announcement_github_body` confirmed to open with the 0.9.2 changelog section
  ahead of the install instructions. This is the check that proves the release
  notes work, and it is now step 5 of the release runbook so it is repeated every
  release.
- `make pre-commit` (fmt, clippy with `-D warnings`, full test suite).
  `crates/cli/tests/cli_integration.rs` asserts the reported version against
  `CARGO_PKG_VERSION`, so it covers the bump to 0.9.2.
- No new code, so no new unit tests. The verification that matters here is the
  `dist plan` output and, after tagging, the rendered release body.
